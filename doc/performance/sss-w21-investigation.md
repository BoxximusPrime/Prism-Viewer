**Measured budget**

CPU/GPU ownership and threading follow-up, September 10: the CPU selects the focus/lights, constructs projection matrices, traverses scene visibility, prepares/sorts geometry and submits OpenGL commands. The GPU rasterizes the entry/exit textures with depth testing; [shadowF.glsl](E:/BoxxyViewer/indra/newview/app_settings/shaders/class1/deferred/shadowF.glsl:38) writes fragment depth and object identity. The final shader also reconstructs/filters thickness from those textures. These maps are not CPU-generated images. There are at most three focused maps total, not three maps per resident.

Threading the whole `generateSSSDepth` function is not an isolated change. `updateCull` writes global `sCull`, visibility state and counters; `stateSort` resets pool draw orders and rebuilds shared geometry. `renderShadow` changes global shadow/camera/matrix/shader state and submits GL draws. The same OpenGL context cannot be current on multiple threads concurrently. Separate contexts are supported but would require resource and completion coordination, not just dispatching the existing method to a worker. [Microsoft WGL context rules](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/nf-wingdi-wglmakecurrent).

A plausible worker task would prepare per-light candidate lists from stable bounds/geometry snapshots, using private output lists, then hand them back for renderer-owned state changes and submission. Measure enough independent preparation work and useful overlap to cover snapshot, dispatch and join costs before attempting that refactor. Entry/exit already share culling and sorting. Further candidates are sharing conservative scene preparation across lights while preserving each light's visibility test, constructing compact positive-ID exit lists, and removing unnecessary geometry invalidations/rebuilds. Off-camera geometry must remain eligible to block light. None of these additional proposals has been implemented or timed.

The first new capture should distinguish preparation from submission/driver waits. Lower resolution primarily reduces GPU pixel work; fewer or less frequent map updates also reduce CPU submissions but can change transmission quality and require correct invalidation for moving subjects, blockers and lights. A geometry rebuild inside the SSS zone is not automatically SSS-specific work or recoverable by moving it elsewhere.

The common baseline is 170 complete frames, mean 30.00 ms/frame, over approximately 5.1 seconds. Timings below are CPU-thread elapsed scopes, including any driver or scheduling delay. They do not measure GPU execution or guaranteed savings. The inspected commit is implementation context; the capture's exact executable revision has not been independently established.

| Scope | Mean per complete frame | p95 | Maximum |
|---|---:|---:|---:|
| SSS depth generation | 5.082 ms | 6.951 ms | 13.912 ms |
| All shadow traversals inside it | 4.676 ms | 6.485 ms | 13.435 ms |

The second row is included in the first. Across all 173 exported SSS invocations, there are 1,024 shadow calls and 512 camera-level sorts: almost three entry/exit pairs per invocation. This agrees with the current three-map implementation. All exported shadow calls are contained in SSS for this capture; this does not mean ordinary shadows never run in other settings.

**Original baseline implementation and work already avoided**

1. [Main display](E:/BoxxyViewer/indra/newview/llviewerdisplay.cpp:819) generates focused depth before the main geometry pass. [Deferred geometry](E:/BoxxyViewer/indra/newview/pipeline.cpp:4068) tags SSS geometry actually drawn and selects the following frame's focus. The focus follows an owning avatar for attachments, retains a nearby subject with hysteresis, and fades changes over about 200 ms. Selection is bounded to the smaller of the configured distance and 32 m.
2. [generateSSSDepth](E:/BoxxyViewer/indra/newview/pipeline.cpp:10475) checks transmission mode, strength, focus validity, main render target, and snapshot/impostor exclusions. It uses a 2.5 m focus radius: one 1024² sun/moon map and up to two 512² local-light maps. Local lights are ranked by linear-light contribution, range and projector intersection; retained lights receive a 1.25 score multiplier and fade between selections.
3. Each map has a front-facing entry pass into RG and a back-facing exit pass into BA, with a depth clear between them. [renderShadow](E:/BoxxyViewer/indra/newview/pipeline.cpp:9821) already reuses culling and sorted draw lists for the exit pass. This optimization is present and should not be proposed again.
4. [setSSSDepthUniforms](E:/BoxxyViewer/indra/newview/pipeline.cpp:10421) assigns frame-local, exactly representable positive object IDs. Unclassified geometry, fullbright surfaces and alpha-BLEND submissions use zero. Zero-ID geometry must block entry rays, but its exit fragments are discarded. Clothes and enclosing walls therefore remain important entry occluders.
5. [Focused path reconstruction](E:/BoxxyViewer/indra/newview/app_settings/shaders/class1/deferred/sssDepthUtil.glsl) filters a 4×4 footprint of raw depth/identity samples, accepting matching positive entry/exit IDs and valid receiver geometry. Confidence/coverage and thickness are separate. The older binary-search helper also exists in this file; its sample count should not be attributed to the focused path.

Precision is part of correctness: projections stay in agent space, their stored matrix uses double precision, and camera translation cancels before conversion for binding. Local-map near-plane tightening is paired with depth clamping and matching CPU culling, so nearby walls continue to block transmission. Replacing the RGBA32F identity/depth format or removing the precision handling needs dedicated optical tests.

Other existing optimizations include skipping forward-alpha sorting/beacons in shadow `postSort`, retaining render targets at their fixed sizes, caching consecutive rigged matrix-palette uploads, and ordinary-shadow batching. They do not eliminate necessary geometry rebuilding or the two actual depth draws per map.

**Correctness gap confirmed in the original baseline**

[pushMaskBatches](E:/BoxxyViewer/indra/newview/lldrawpool.cpp:572) merges adjacent unrigged ranges for three ordinary mask/tree shader objects whenever shadow rendering is active. Its merge key checks buffers, transforms, index adjacency, alpha cutoff and texture state, but at baseline had no SSS-pass guard or object-identity comparison. Those same shader objects write `sss_depth_id` during focused depth capture.

[registerFace](E:/BoxxyViewer/indra/newview/llvovolume.cpp:5755) correctly splits draw infos at SSS object boundaries. The later merge can undo that split. [pushBatchRange](E:/BoxxyViewer/indra/newview/lldrawpool.cpp:718) calls `applyModelMatrix` once with the first draw's metadata, so every index in the combined range receives its identity.

The [production-loop diagnostic](E:/BoxxyViewer/output/w21-tracy-research/reproduce_sss_mask_identity.py) reproduces the mismatch: two six-index ranges expected to carry IDs 11 and 22 are submitted as one range with ID 11 throughout. It checks 18 synthetic combinations across indexed/nonindexed submission and the three shader objects, including effective zero-ID boundaries. Fullbright combinations test the missing state boundary; they are not proof that every fixture combination arises in a real render pool. This is a CPU state-recorder reproduction of the batching defect, not an observed screenshot artifact or proof that it occurred in w21. Rigged batches take a separate path.

First implementation step: either disable this late merge during SSS, matching the existing untextured guard, or require identical effective SSS identity as well as all existing keys. The former is the smallest correctness patch; the latter retains more batching. Add an actual identity-preservation regression before broadening SSS batching. The diagnostic reads the original commit and expects its unfixed mismatch and must not be mistaken for a passing regression test after a fix.

All eight inspected shadow fragment variants discard such fragments. | Preserve every entry blocker and every positive-ID exit. Start with complete alpha-BLEND exit traversal, then cover individual simple/mask/PBR/rigged draw infos after fixing identity boundaries. Counts for the broader opportunity are not captured yet. |
| 2 | Allow compatible unrigged SSS depth batches with identical effective identity. | 4 | Cache or reduce focused-map updates only after the above work is measured. | This is a quality/invalidation tradeoff: avatar poses, occluders, focus, light transforms, fades, IDs and origin changes can all invalidate a map. Fixed alternating updates would risk stale thickness and flicker. |

The narrow alpha-BLEND opportunity has a measured limit. [renderAlphaObjects](E:/BoxxyViewer/indra/newview/pipeline.cpp:6966) sets `mSSSDepthOpaque=false`, making all its exit fragments zero-ID. Inferring entry/exit from each map's ordered pair gives **0.0448 ms/frame in exit alpha traversal**, versus 0.0543 ms/frame at entry. There are 1,006 calls in each category over 170 frames, including rigged and unrigged traversals. The [phase analysis](E:/BoxxyViewer/output/w21-tracy-research/summarize_sss_exit.py) asserts containment, two alpha calls per shadow scope, and even pairing; the trace does not directly label the phase. This is a small CPU opportunity, not an explanation for the whole 5.08 ms. GPU savings and other zero-ID draws remain unmeasured. [Phase results](E:/BoxxyViewer/output/w21-tracy-research/sss-alpha-phase-summary.json).

The worst frame starts 3.112 s into the analyzed interval: 43.44 ms total, 13.91 ms SSS, with one 9.92 ms shadow traversal containing 9.25 ms sort, 9.10 ms post-sort and **7.28 ms priority geometry rebuild**. Individual geometry rebuilds include 1.30, 1.21 and 2.18 ms. SSS self time there is only 0.47 ms. [postSort](E:/BoxxyViewer/indra/newview/pipeline.cpp:3646) drains [priority groups](E:/BoxxyViewer/indra/newview/pipeline.cpp:2886) and flushes dirty meshes, so its location can inherit general geometry work. Record queue sizes, rebuild reasons and actual group counts before changing scheduling. Moving the same 7.28 ms earlier does not recover it.

A second frame at 4.294 s spends 10.35 ms in SSS with 7.47 ms self time. That needs narrow timing around target binding/clearing/flushing, state queries, attachment visibility and setup. It should not automatically be assigned the first frame's rebuild cause. Lower map resolution may reduce GPU work; it would not directly remove CPU culling, sorting or submission.

**Further CPU reductions and time slicing — discussion follow-up**

The user prefers exploring alternatives to threading and asks whether time slicing would cause avatar flicker. No additional production change was made for this discussion.

- Audit complete empty or zero-contribution shadow categories before shader binding, matrix reset, pool setup and iteration. The first pass skips individual zero-ID exit draws and the alpha-BLEND traversal, but `renderShadow` still visits simple/fullbright/mask/grass/PBR categories and `renderGeomShadow` still sets up face pools. `renderObjects` resets matrices even around empty lists. Whole-category omission could remove CPU setup without reducing map frequency. Verify pool-specific identity overrides before skipping face pools; `renderGLTFObjects` also invokes the separate GLTF scene manager, so an empty draw-info list alone does not prove that wrapper has nothing to render.
- Prepare compact compatible draw ranges and exit lists once per light and reuse them between its two passes. The entry/exit cull and sort are already shared; this proposal targets remaining repeated classification, dispatch and state setup. Preserve effective identity, alpha/texture/culling state, equal-depth ordering and rigged palettes. Added list construction must save more work than it introduces.
- Do not propose caching joint-matrix calculation per frame as new work: `LLVOAvatar::updateSkinInfoMatrixPalette` already checks its cache's `mFrame` against `gFrameCount`. Consecutive palette uploads are cached too. Any further optimization needs evidence of repeated uploads or setup across category/shader boundaries and must track the actual shader state.
- Static blocker depth caching is a larger optional experiment: retain fixed environment entry depth, refresh dynamic casters every frame, and preserve the nearest entry depth and its corresponding identity. Static/dynamic shadow caching is an established technique for ordinary shadows; applying it to these paired depth/identity maps is a separate proposal. [NVIDIA GPU Gems 3, local shadow maps](https://developer.nvidia.com/gpugems/gpugems3/part-iii-rendering/chapter-19-deferred-shading-tabula-rasa). Focused projections follow the subject, so camera/light/focus projection changes, object motion, alpha/material changes and geometry streaming can invalidate the cache. Extra copies/storage and frequent invalidation may eliminate the benefit. A stationary light alone is insufficient.

Time slicing should retain a complete old map until a complete replacement is ready. The avatar mesh would still animate every frame; the expected risk is stale transmission that lags, shimmers or pops on moving fingers, faces, bodies and blockers. At a 30 FPS render rate, rotating one of three maps per frame refreshes each map at only 10 Hz. This is an illustrative schedule, not a measured performance prediction.

Never render entry from one pose/frame and exit from another: the thickness shader requires matched depth layers and object IDs, and IDs are assigned afresh each capture. Retained textures must keep their captured projection/light metadata. These shaders also check the current receiver against the captured exit surface, so stale poses can reduce coverage. Interpolating raw depths or categorical IDs is not a valid general fix; blending final lighting would need separate history rejection to avoid trails.

If update reduction is eventually tested, prefer change-driven reuse while the entire relevant scene state is unchanged, or give weak secondary lights a lower refresh priority while dominant lighting stays current. A stationary avatar root does not imply a stationary pose. Nearby dancing avatars are likely to invalidate exact caches frequently. First compare the new capture, then test category/setup omission before changing visual update policy.

**Distance or projected-size quality — discussion follow-up**

The distance calculation is not a material obstacle. `updateSSSDepthFocus` already computes squared camera distance for eligible draw infos, without square roots, and caps focus selection to `min(BoxxySSSMaxDistance, 32 m)`. Choosing a quality tier once for the retained focus would add very little arithmetic compared with culling and issuing depth draws. The maps inside that range currently use fixed resolutions and up to three lights.

For CPU savings, change how many depth-map pairs are rendered, or fade out focused depth transmission and stop rendering its maps when the subject is sufficiently small. Reducing texture resolution or filter taps mostly reduces GPU work while retaining the same CPU scene traversal and draw submissions. A proposed tier scheme is full available maps for a large subject, fewer important light maps for a smaller subject, and no focused depth maps after the transmission contribution has faded away. Retained maps still update each frame. This is an appearance/performance option, not equivalent output.

Prefer projected subject size, including FOV/zoom and viewport height, over fixed distance alone; a distant zoomed-in face can still need high detail. The relationship between view distance, FOV and required shadow sampling density is described in [NVIDIA GPU Gems 3, parallel-split shadow maps](https://developer.nvidia.com/gpugems/gpugems3/part-ii-light-and-shadows/chapter-10-parallel-split-shadow-maps-programmable-gpus). Applying projected-size thresholds to this focused SSS implementation is our proposed policy, not that chapter's algorithm. Use different promotion/demotion thresholds and smooth contribution fades so small camera movement does not repeatedly switch tiers. Avoid repeated render-target reallocation at a threshold.

Limits: there is one focused cluster, not independent map sets per avatar. A nearby, large focused avatar can keep full map cost even if the other residents are distant. The potential saving therefore depends on the actual focus and framing. Do not discard light blockers based on their own camera distance; off-camera or distant geometry can still occlude a retained light. No distance-quality changes or new thresholds have been implemented.
