# Crowded-scene draw preparation — 2026-10-11

Status: implementation, regression checks, Release rebuild, remembered login and two post-build captures completed. Changes are uncommitted; performance gain remains unproven.

Follow-up: [full CPU shadow-pass measurements and engine/threading candidates](shadow-cpu-2026-10-11.md) establish that draw submission is substantially more expensive than the preparation timer alone.

## Setup and interpretation

- Scene: Mystic Harbor, crowded gathering outside a building. Residents, animations, particles, streaming and lighting remain live.
- NVIDIA GeForce RTX 5090; driver reported by the viewer: `4.6.0 NVIDIA 617.14`.

- Raw JSON files include per-frame samples, full graphics settings, environment, start/end camera, viewport and executable identity. Artifacts live under `.logs/viewer-mcp/` and `output/`; keep these local files with this report when archiving the investigation.

## Diagnostic Tracy trace

A 15-second Tracy capture contains 121 complete main-thread frame scopes. Its instrumentation is very expensive in this scene: mean frame time is 123.44 ms, versus roughly 34–42 ms in the MCP captures. Use this trace to identify repeated calls and enclosing work, not as a normal-FPS benchmark.

- Camera-level `stateSort` ran 2,658 times, averaging 21.97 calls per frame across shadows, SSS, hair, impostors and other views.
- Shadow generation contained about 60% of traced draw-preparation time: 5.592 ms/frame out of 9.280 ms/frame. These are trace means, not normal-running costs.
- Priority geometry rebuilds averaged 2.714 ms/frame in the trace; 2.465 ms occurred inside shadow preparation.
- All eight largest individual draw-preparation calls occurred in shadow generation and were dominated by priority rebuilds. The largest took 10.037 ms, including 8.758 ms of priority rebuild work.
- Across the complete export, the volume `rebuildMesh` function was called 747,615 times, while its dirty-work body ran only 1,917 times. Most dispatches immediately returned.

Artifacts: [trace](../../output/draw-sort-20261011/baseline-1.tracy), [analysis script](../../output/draw-sort-20261011/analyze.py), [summary](../../output/draw-sort-20261011/summary.json). The summary attributes complete main-thread scopes by timestamp containment; exports alongside it preserve the underlying events.

## Implemented change

`LLSpatialGroup::rebuildMesh` now checks `MESH_DIRTY` before calling the partition's virtual rebuild method. Current implementations already do no work for clean groups. A group dirtied again during a later pass still rebuilds immediately; this does not cache a once-per-frame decision or postpone geometry updates.

The existing CPU capture machinery now splits draw preparation by world, shadow, reflection, SSS, hair, impostor and HUD views. Additional scopes measure post-sort geometry rebuilds, priority work, mesh completion notifications, render-map assembly, deferred mesh packing, alpha ordering and buffer uploads. Volume, particle and mesh scopes measure actual dirty-work bodies.

The clean-group change removes redundant dispatches, but their measured trace cost is small relative to total draw preparation. Geometry scheduling changes are deferred until the lighter MCP scopes establish their actual cost. No performance improvement is claimed from the trace alone.

### Comparison limits

Viewport and render dimensions matched, and sky/water metadata matched across restart. The initial login camera moved about 1.246 m and rotated 6.386 degrees. It was deliberately left untouched. Graphics values also changed across restart; no `graphics_set` or camera mutation was issued in this session. Selected recorded changes:

| Setting | Before restart | After restart |
| --- | ---: | ---: |
| `RenderFarClip` | 128.0 | 112.0 |
| `RenderShadowDetail` | 2 | 1.0 |
| `RenderGTAOQuality` | 1 | 2 |
| `RenderPCSSQuality` | 0 | 1 |
| `RenderPCSSCleanup` | 3.0 | 2 |
| `BoxxySSSDepth` | 0.05000000074505806 | 0.027000000700354576 |
| `BoxxyHairShine` | 0.3499999940395355 | 2.0 |
| `RenderAnisotropic` | False | True |

The cause of these loaded-value differences was not investigated. The complete differences are retained in the comparison JSON, including numeric representation changes. The two post-build captures kept the same camera, settings, sky/water and viewport throughout. The additional CPU checkpoints also change instrumentation overhead. **Do not report the lower draw-preparation median as a measured optimization win.**

Next useful target: inspect why priority geometry rebuilds and deferred mesh packing recur during shadow preparation, and isolate occasional buffer-flush stalls. Any scheduling change must preserve groups dirtied later in the same frame. A controlled performance claim requires matching camera/settings/instrumentation on both builds and repeated visual comparisons.
